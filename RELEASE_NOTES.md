# VGRPresenter 0.0.8

## What's new

## Improvements

- The NDI program feed's plan is worked out off the thread that draws. While a show is live, ten times a second, the feed re-resolved what to send — the first enabled NDI output, the display provider behind it and that output's own frame buffer — and the provider map and the render registry are engine singletons with their own locks, so the poll that keeps the network fed was taking them on the interface thread next to the live show. The resolution is now split by ownership: the roster read, the published NDI status, the buffer name and every piece of the send indicator's state stay where the caller is, and the engine walk (the provider lookup, the buffer lookup, its enabled flag and one frame snapshot) runs on a worker whose answer is published back on the interface thread — the same accepted-then-published shape the tap opens already use. The feed itself is unchanged: its own clock, its own rate, its own skip-under-backpressure pacing, and a rename or a rate change still reaches the wire within one poll.
- The scripture and search panels no longer read the Bible on the thread that draws. The installed-Bible list, a Bible's book outline, one chapter's verses, the resolution of a typed reference and a full query were each answered by asking the engine directly — a lock and a copy per question — from panel bindings, from the text field's completer on every keystroke and from the hover preview of a search hit. Each answer is now read once on a worker and kept as the published value: the panel asks a lookup, a question nobody has asked before is queued and answered a moment later (the completer re-asks when it lands, so a typed reference still jumps and the book list still collapses to it), and a chapter's rows or a hovered verse arrive on the row that is still being shown. The engine work itself is untouched — the same reads, on a worker, which is where the chapter and search paths already ran them.
- The Plugins screen's feature list is published rather than read through. The card that lists the engine's features and their switches read the runtime's registry — a lock and a copy — from a binding, once per change. The list is now walked on a worker and published, and a flipped switch reaches the screen when the fresh list lands, carrying the engine's real state rather than a locally patched one.
- The interface-thread guard is working from the right lines now, and that is what closed the last two clusters. Five repairs went in, each of them a case of a correct rule reporting the wrong thing: a helper that posts its device work to a worker and returns no longer makes every command that reaches it look blocking; a lambda posted through a thread pool is recognised as off-thread (the span rule had been reading the pool's own `globalInstance()` call and leaving the work on the caller); `lastFrame = QImage();` is no longer counted as a data load; a class NAME is no longer counted as file I/O, so `QDir::fromNativeSeparators(path)` and `QFileInfo(path).fileName()` (string arithmetic, no disk) stopped flagging three show-file operations for a line that touches nothing — and a new `document I/O` label names the seam that really writes, which surfaced five more show-file operations the old match had been hiding; and property declarations are now judged in files with Windows line endings, where every `Q_PROPERTY` had been silently skipped (`ScriptureService::bibles` and the Plugins list were never looked at). With the guard reading the right lines, its inventory was worked down cluster by cluster until it was empty — what `--all` has left to print is nothing, and every finding prints the offending line under it, so the next pass does not have to guess which call earned it.
- A passage list is divided before it is clicked, not by it. A long sermon paragraph used to sit on the list as one long line until it was picked, because each row was divided only for the passage already chosen — the operator could not see where the passage would break without clicking it, and the work of dividing it then landed on the interface thread at the moment of the click, which is exactly when a service cannot afford a pause. With "Divide long …" switched on, the sermon or chapter on screen is now divided as it opens, in the background, and its continuations are on the list straight away (paragraph 2 shown as 2, 2-1, 2-2 …): choosing one is a lookup rather than a calculation, and the list no longer rebuilds itself on every click. Anything that would make that listing wrong — a different template, a division option moved, a sermon imported — divides the open passage again in the background instead of leaving the old division on screen.
- Nothing that waits on the operating system runs on the thread that draws any more. The app's own hang reports had already named the calls that froze the window — a meter read waiting on a lock the audio capture thread held, a settings change waiting on the resource sampler's lock, the clipboard open waiting out another process's write, the backup timer copying the open show — and each of them has now been moved off the interface thread and answers with a signal when it is done: backups, backup listings, restores and deletes, the crash-recovery store, and the clipboard read (and a screenshot's picture encode with it). A settings change is written as before and pushed to the engine in the background, and a burst of changes — dragging a slider — coalesces into one push with the last value winning rather than one push per tick.
- The audio meters can no longer hold up the window. A device's captured audio used to take the meter table's lock once per sample frame — tens of thousands of times a second — while the interface thread read the same table twenty times a second to draw the levels, and on a busy machine (which is when audio matters) the interface thread lost that race for seconds at a time: one of the app's hang reports has it frozen in exactly that wait. The capture side now takes that lock once per audio packet, and the level read never waits at all — it takes the reading it can get and repeats the previous one for that single tick if a worker is mid-write, with the tap list itself versioned so a removed input still reads as no signal immediately. Same meters, same numbers, no waiting.
- The meters, the device list and the NDI permission prompt no longer work on the thread that draws. Three surfaces still did their device work there: opening or closing an audio meter (the capture session is joined and rebuilt on that call), the SDI half of every device refresh (the `sdi` plugin's provider probe plus a COM walk of the DeckLink cards, paid again on every settings visit, display-mode change, boot sweep and plugin toggle), and the NDI firewall pair (a hidden `netsh` child process per probe, and an elevated one when the rule has to be added). Each now keeps its bookkeeping where the caller is — the refcounted hold tables, the tap ids, the device roster, the feature gate — and hands the device call to a worker, publishing the answer on the interface thread when it arrives. That includes the answers that used to be return values: the firewall request reports its outcome as a signal, and the retry timer's probe as its own, so the Outputs screen and the Plugins toggle now act where the answer lands instead of waiting for it. A meter tap is claimed before it is opened, so a dialog closed in the same breath still closes the capture session it just asked for, and a refused tap leaves its loud reason in the log exactly as it did. Measured in the running app on this machine: the media meter chain — a real decode through the queued open, and a refusal through the marshalled verdict — passes unchanged (`MEDIAMETER: PASS live=20.20 silent=0 stored=4 agree=PASS`, `tools/selftest/run_media_meter_test.sh`), and the interface-thread guard now reports `0 known, 0 new HARD, 77 already off-thread` with an empty baseline ledger (`tools/gui_thread_baseline.json`), so a wait of this kind fails the build from now on rather than being recorded as a plan.
- Every search box in the app now waits for typing to stop rather than querying the engine per keystroke. The six library tabs share one search box, and typing into it re-filtered the pane on every character — and each pane answers a filter with an engine query (the show library, the media scan, the design scans, the sermon corpus). One short pause now sits in the single place those tabs share, so typing stays instant and a fast typist costs one query instead of one per letter; a query typed just before switching tabs still lands on the tab it was typed on. The settings search box got the same treatment, and two paths that scanned the whole vocabulary synchronously — the quick-search correction on Tab, and the diagnostic that printed a row count from inside a log line — now ask the engine and use the answer when it arrives.
- The mix board and the audio/video cards no longer push their state at the engine from the thread that draws. Every fader move, mute, L/R pill and routing-matrix cell carried its own change straight into the production graph on the interface thread — and the graph serializes and re-validates itself on each change, which is why a dragged fader could stutter the window it was being dragged in. Those writes now go to the engine worker in the order they were made (the last value of a drag wins), and the same is true of the machine sample behind Settings · Smart Config, the existence check behind a style's background picture (a picture on a network share no longer parks the window while the share answers, or does not) and the name shown when a media folder is removed, which is now worked out from the path rather than by asking the filesystem about a folder that may already be gone.
- The resource dials no longer read the machine on the thread that draws. The health card, Smart Config's live budgets and the resource health modal get their numbers from a platform sample — system times, memory, disk free space, the network interface table, the power status — and that sampling ran on the interface thread twice a second. On a machine already working hard, one slow sample could hold up the interface while the operator was presenting; the sample is now taken on a thread of its own and only the finished numbers are handed back, so the thread that draws never waits on the platform. The numbers QML binds are unchanged: the same shapes (a reading the platform cannot give still reads -1, never a fake 0), published only when a number actually moves.
- The diagnostics the app ships with are checked, not assumed. A stall or a crash is written down by a debugging tool bundled inside the install, and that tool's own libraries used to be listed by hand — a list that had already gone stale, so the tool shipped unable to start. The package now works out what the tool needs by reading the tool's own dependency list, copies all of it, and starts the tool once while the package is being built, on a stripped-down environment (System32 only — exactly what a machine with no developer tools on it resolves). A tool that cannot run now stops the package being built instead of reaching a customer.
- Stepping to the next passage no longer waits on anything. A passage's slides are worked out ahead of the click (the list has shown its paragraph breaks since the last release), but a *step* — the ‹ › beside a verse, or moving on to the next sermon in a collection — still read the next chapter from the library at the moment the operator was presenting. The passages on either side of the one on screen are now read and prepared in the background as well, so the step is served from what is already in hand: no read, no fill, nothing left to wait for. Three passages are kept per tab — the one on screen and one on each side — and the passage being presented is never the one dropped to make room, whichever tab the operator is stepping in. The app's log says which passages were read ahead and how long that took, and says so plainly when a step was served without reading anything at all.
- Opening a long sermon costs what the first screenful costs, not what the sermon costs. The background division that puts a passage's paragraph breaks on the list (see above) was made for the WHOLE passage before the list could appear, and a sermon in a real library runs to hundreds of paragraphs — 500 in the longest one here — so the operator waited for all of them, and every step read the two neighbouring sermons just as completely. The passage on screen is now divided to its HEAD, about four screens' worth of rows, which is all a list can show at once; its rows are handed over as soon as that much is cut, and the rest of the passage is divided immediately behind them and handed over again when it lands — so a paragraph below the fold still arrives already divided, without ever being clicked. Measured in the running app on this machine's own library, the longest sermon in it (499 paragraphs, 2,907 list rows): dividing for the open fell from 111 ms to 4 ms, and the time from the click to the rows on screen from 231 ms to 125 ms, with the remaining 484 paragraphs divided while the list was already live. The passages on either side are read with their heads cut the same way, and stepping into one divides the rest as it opens. The list keeps its place across that second hand-over: the row the operator is reading stays the row they are reading instead of the view sliding as rows appear above it.
- Saving, opening and reading a show no longer happen on the thread that draws. Ten operations — save, save-as, the recovery copy, open, the centre page's peek, the next timer, the slide menu's edits, the two template calls and the text rewrite — drove the engine's document API straight from the screen, and that API is synchronous by design: one JSON document, written or parsed where the operator was standing, on a path that can be a network share. The writes are handed to the engine's worker now and answer when they land, with the toast, the "the show changed" notice, the library refresh and the log line all arriving with that answer rather than in front of the operator's click. What the screen READS is read the same way and then kept: the centre page's preview asks a lookup and re-reads itself when the answer arrives — it is told by a revision that really moves now, where publishing an answer used to announce a change without changing the value — and anything that writes that show drops the kept answer, so the read after a save is the file that was just written rather than the one before it. Verified end to end against real files by a new harness, `tools/selftest/run_show_io_test.sh`, which drives the whole chain in the running app and checks each verdict AND the artifact behind it (the file on disk, the `pending` answer for a show nobody has read yet, the dropped answer after a write, the moving revision, and the app's own clean exit): `SHOWIO: PASS save=ok open=ok peek=ok timer=ok copy=ok steps=9`.
- The app now checks its own diagnostics on every launch, and says so when they cannot work. Everything that writes a crash or a hang down for later — the bundled debugging tool, the shortcut that reads a report, the dump writer, the folder the reports go into — was previously found to be broken only when someone needed it, after the fact: a debugging tool whose own library was missing did not fail loudly, it simply produced an empty file. The app now runs the same chain a real capture would, at startup and in the background: it starts the debugger it would attach and insists it answers, confirms the dump writer is present, and opens the folder it writes into. A healthy machine gets one line saying so; a broken one gets a warning naming every part that is wrong and what it costs — so a report that could not be produced is known before a crash, not discovered after one. And the verdict is no longer only in the log: Settings · General has a "Crash reports" row that says whether a crash on this machine can be captured and read, naming every broken part when it cannot — and when a launch is reporting a crash from last time while that tooling is broken, the notice now says so too, because "details were written to the crash log" is not true on a machine where nothing was.
- The sermon tab's own result lists build the rows you can see, not the whole list you cannot. Typing two characters into the library search on The Table lists every sermon whose citation carries them — 641 of them in a 1,206-sermon library — and all three lists that answer a search were built in full the moment the rows arrived: the citation list, the sermon the pointer opens beside it (277 paragraphs for the first match here), and the pane's own search results. One query was 918 list rows built in one go, at exactly the moment the pointer was supposed to feel instant. Each is now a windowed list that builds a viewport's worth of rows (21, 5 and 20 for the same query) and still reaches its last row when scrolled, so the end of a 641-match list is a scroll away instead of a stall. Measured in the running app on this machine's library, including the scroll to the end of each list (`tools/selftest/run_pane_rows_test.sh`).
- A note or a highlight on a verse now costs the click, not the Bible. Marking a verse used to read the whole installed scripture, parse it and write it back — megabytes of verse text, on the thread that draws, under the same lock every chapter read takes (5.8 MB for one Bible in this library). The notes and highlights now live in their own small file beside the scripture, so a mark writes kilobytes that contain no verse text at all, and the scripture itself is not opened: the app measures both halves of every mark and says so in its log (`user-data sidecar written in N ms (B bytes …); corpus untouched`), and the same log now names the rare write that IS the scripture (`store written (corpus) in N ms`), so a mark that ever goes back to rewriting it is visible. Measured in the running app on this machine's own library: a highlight toggle and a note save cost the interface thread tens of milliseconds each and the sidecar write inside them 2-11 ms, while the same corpus takes 32-67 ms to rewrite — 15-23x cheaper per mark (`tools/selftest/run_mark_sidecar_test.sh`, which marks a verse and undoes it, then checks both files byte for byte).
- The lock guard now reads the whole engine, not one file at a time — and no longer passes a clean verdict it cannot justify. The rule that catches a lock held across a disk or device call through a helper only ever looked inside the file in front of it, and it treated a `namespace` wrapper as an opaque block, so a namespaced file contributed no definitions at all: a whole class of locks read as clean. Both halves are fixed, and the rule's own verdict is now checked before the real scan — eight small shapes in `tools/lock_scope_fixtures` whose expected result is known, run by every build, so a rule that stops firing fails the build instead of quietly approving everything (a locked line calling a helper in ANOTHER file must be flagged; re-locking the same mutex must be flagged; the same shape on a recursive mutex, another class's equally-named mutex, or an ambiguous helper name must not). What turning it on revealed — 71 pre-existing sites where a module lock is held across a store write, a folder scan, a provider call or an event dispatch — is recorded with its fix plan rather than waived away, and the guard prints what it refuses to judge (a call on another object whose type it cannot know, a lock declared inside a macro, a helper handed the lock to release) instead of guessing.
- A stalled interface is no longer made worse by the report about it. Attaching the debugging tool suspends every thread while it walks them, and the app could attach it a second and third time on each new report — so one slow stall turned into a run of them, each one re-freezing the very thread it was trying to diagnose. One capture now runs at a time and not again within a minute, so a single stall produces one honest report rather than a cascade of them.

## Fixes

- A stalled app no longer answers with a system error dialog about its own diagnostics. When the interface stops responding, the app attaches its bundled debugging tool to itself and writes down what every thread was doing. The copy of that tool in the installed folder could not start, because a library it needs one step further down its chain was never copied beside it, so in place of a report the operator got a modal "the code execution cannot proceed because …dll was not found" box from the tool itself, sitting on top of the frozen window it was meant to explain. Behind it, the file the report would have gone into was empty — the app recorded that a capture had been taken when nothing had been written at all. The tool now carries everything it needs, a capture that produced nothing is reported as failed instead of present, and an empty file is not left behind to be mistaken for evidence. The minidump is unaffected: it already held every thread's stack, and still does.
- The app's own record of a hang now says which of its two halves worked. The minidump (every thread's stack, readable offline) and the symbolized backtrace (the half that names the blocked call in plain words) are written as two separate lines that each stand on their own, so a record reading "capture failed" points you at the dump for the answer instead of at a file that has nothing in it.
